PROTOCOL NOTE

Why AEP1 exists

AEP1 sits in an awkward gap between several established layers:

  • Audio containers such as fMP4, Matroska and WAV group tracks, but are designed mainly for storage or HTTP delivery.
  • RTP/WebRTC synchronizes live streams using timestamps, SSRCs and RTCP, but treats tracks as separate packet flows.
  • AES67, Ravenna and ST 2110-30 handle synchronized professional PCM transport, but not arbitrary codec-independent production payloads.
  • ADM/BWF describes multichannel production relationships, but is primarily file metadata.
  • FEC protocols protect bytes, but generally do not understand synchronized audio-track epochs.

AEP1’s useful idea is narrower:

“These Soundkit v2 frames from different tracks belong to the same small, synchronized production instant.”

That makes the whole epoch a convenient unit for routing, buffering, validation, replay and RaptorQ protection. It also keeps codec details inside Soundkit v2 rather than embedding FLAC, Opus or PCM assumptions into the mesh.

There is no dominant standard because most systems historically chose one of two models:

  1. Transport every channel or track as an independently timestamped stream.
  2. Package everything into a comparatively heavyweight media container.

AEP1 occupies the middle: lightweight like a packet protocol, synchronized like a container, codec-independent, and explicitly designed for multitrack production over a distributed mesh.

01 / INGEST

Contribution adapters

Accept live audio, video, and data through format-specific adapters, then convert them into versioned streaming payloads for the mesh.

  • RIST and production contribution
  • Soundkit v2 audio payloads
  • Media format remains explicit
02 / MESH

Multi-parent transport

Forward payloads over primary and warm repair paths with bounded queues, erasure repair, deterministic generations, and service-owned telemetry.

  • Horizontally scalable relay DAG
  • RaptorQ repair paths
  • Measured failover state
03 / EDGE

Regional publication

Materialize the same canonical media stream at playback edges and package locally for low-latency HTTP delivery.

  • LL-HLS at every active region
  • Audio, video, and sidechannels
  • Independent reader capacity
